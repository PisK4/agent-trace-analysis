## Question

系统调研外部 Agent 评估体系，把谱系核准到最新，产出「可吸取清单」写回本票。重点四块：

1. **本地优先评测框架**（promptfoo、DeepEval、inspect_ai）：配置即代码的具体工程形态；
2. **可靠性指标**：tau-bench 的 pass^k 及其他值得借的 agent 可靠性指标；
3. **轨迹级评判**：Agent-as-a-Judge 一类工作的评判单位与判据设计；
4. **失败模式分类学**：现成的 agent failure taxonomy 清单，供 T2 当编码本。

每条结论注明来源与采纳前提。两条硬约束：本地优先（无服务端）；接入面只走轨迹翻译。

## Resolution

2026-08-23 调研完成（WebSearch 核准谱系至 2026-08，深读下列来源）。可吸取清单：

### 一、失败模式分类学 —— 直接喂给 T2 当编码本

| 来源 | 内容 | 采纳方式 |
| --- | --- | --- |
| AgentErrorTaxonomy（arXiv:2509.25370，UIUC AgentDebug） | 按 agent 模块分的失败模式：记忆、反思、规划、行动、系统级五类；配套 AgentErrorBench 标注轨迹集与根因定位方法 | **编码本主骨架**：拿这五类到 Cue 语料里逐类验证 |
| 六簇综合（arXiv:2607.05775 的公开转述，CAI 2026-07） | 工具调用错误、规划与约束违背、长程退化、多智能体协作失败、安全失败、测量有效性问题 | 前四簇并入编码本；"测量有效性"一簇转化为自查项：警惕"子任务全绿、端到端全红"的分歧 |
| 厂商词表（Confident 等生产监测分类） | 工具误用、上下文丢失、目标漂移、静默质量退化、检索失败、策略违规 | 补充词表，Cue 语料验证后取舍 |

关键事实一条：单步成功率 95% 在 25 步任务里只剩约 28% 完成率——**失败随步数非线性复合**（六簇文引的多篇基准一致结论）。这把"步数"抬成一等指标。

### 二、指标设计 —— 喂给 T5

- **pass^k**（tau-bench，arXiv:2406.12045，Sierra）：同一任务独立跑 k 次、全部通过的概率，度量可靠性一致性而非平均成功率。采纳为候选指标；与 T3 决议"多次 run 取均值"互补——均值看期望，pass^k 看最差情况与方差，"时好时坏"的 agent 在它面前无处藏身。
- **分歧指标**：子任务成功率与端到端成功率分开统计、对比着看，分歧本身就是告警信号（源自六簇文的"reliability lie"论点）。ata 投影层的 turn/step 结构天然支持这个拆分。

### 三、轨迹级评判 —— 喂给 T4

- **Agent-as-a-Judge**（arXiv:2410.10934 原文；arXiv:2601.05111 综述）：评判对象是整条轨迹和中间阶段，不是只看最终答案；做法是由一个 agent 调查另一个 agent 的行为再下判。
- 采纳其立场（评过程不只评结果），落地载体就是 T4-D 的结构化标注；但综述明确指出 agentic 全自动判官**推理成本高**——所以分期：第一期规则检测 + 用户人标注（T9 已决），LLM 判官作为后续可选增强，不进首版。

### 四、工程形态 —— 本地优先三家的共同答案

- **promptfoo**：YAML 配置（prompts / providers / tests / assertions）加一条 CLI 命令出结果，本地视图查看；
- **DeepEval**：pytest 风格断言式指标，适合日后把回归集挂进 CI；
- **inspect_ai**（UK AISI）：task / solver / scorer 三段式，评测结果落 .json 日志文件配本地查看器。

三家共同点恰好确认 T3 决议的方向：**任务集是文件、跑批是命令、结果是文件、版本靠 git，全程无服务端**。promptfoo 的配置文件形状可作为我们回归任务集目录结构的直接参照。

### 明确不吸取

- 服务端平台部署形态（地图 Notes 已裁决）；
- 全自动 LLM 判官（首版不做，理由见第三节）；
- 公开基准任务集（WebArena/tau-bench 的任务本身），只借指标定义。
